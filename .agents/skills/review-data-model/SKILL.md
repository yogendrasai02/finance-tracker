# Review Data Model

Review the data model as a senior/principal engineer with a focus on financial data.
The goal is to verify relational integrity, prevent data corruption, ensure tenant isolation, and check indexing before migrations or ORM entities are written.

The default target is `docs/DATA_MODEL.md` unless the user names another file.

This is a review, not a rewrite. Point to specific tables, columns, or relationships and suggest. Do not edit the model unless the user asks.

## Review process

1. **Read context.**
   - Read the data model in full.
   - Read `docs/SPEC.md` to check the model actually supports every feature and flow.
2. **Apply the checklist** against the table definitions and any ER diagram. Find missing constraints, dangerous types, indexing gaps, and normalization flaws.
3. **Classify findings** by severity (see below).
4. **Produce the structured report** using the template.

## Review objectives

Judge the model against five standards:

1. **Precision and money correctness** — zero floating-point risk, unambiguous sign convention.
2. **Multi-tenancy scoping** — tenant isolation enforced structurally on every user-owned entity from day 1.
3. **Ledger integrity and immutability** — raw imported input separated from normalized ledger rows, full auditability.
4. **Relational constraints and schema hygiene** — keys, foreign keys, cascades, nullability correct.
5. **Performance and indexing** — indexes match real access paths without redundant bloat.

## Checklist

### Correctness of financial data
- Is money stored as integer minor units (e.g. `BIGINT` paise) or fixed-precision decimal, never floating point (`FLOAT`/`DOUBLE`/`REAL`)?
- Is currency stored per amount (not assumed), even if INR is the only one today?
- Sign convention:
  - Is there a single global sign rule across all account types (e.g. positive = inflow/credit, negative = outflow/debit)?
  - Does the model avoid inverted signs between asset and liability accounts?
  - Is the convention documented?
- Can amounts be aggregated correctly across accounts and time?
- Timestamps:
  - Are timestamps timezone-aware (`TIMESTAMPTZ`) where they record events?
  - Are transaction dates stored as calendar `DATE` without a time component?
- Are fixed value sets stored as `TEXT` + `CHECK` (migration-friendly) rather than native DB enums where enums complicate migration/ORM?

### Auditability, raw ingestion, and traceability
- Can every transaction be traced back to its source statement and source row?
- Raw preservation:
  - Are statement imports recorded in a separate raw table (e.g. `statement_import_rows`) storing verbatim text?
  - Can raw rows be inspected or re-parsed if parsing logic changes later?
- Fact vs. interpretation:
  - Are immutable bank facts (date, amount, raw narration, account) protected from mutation?
  - Are mutable user interpretations (category, notes, tags) decoupled from the raw facts?
- Is there a record of how a transaction was categorized (manual, rule, import)?
- Are corrections handled without silently destroying the original value?
- Are created/updated timestamps present where they matter?

### Integrity constraints
- Are primary keys and foreign keys defined for every relationship?
- Primary key strategy: uniform and index-friendly (e.g. `BIGINT GENERATED BY DEFAULT AS IDENTITY`)?
- Foreign key cascades:
  - Is `ON DELETE` behavior explicitly chosen (`RESTRICT`, `CASCADE`, `SET NULL`)?
  - Are hard cascades prevented on financial ledger records?
- Are uniqueness constraints present where duplicates would be wrong (e.g. re-importing the same statement)?
- Deduplication:
  - Is there a deterministic dedup fingerprint or unique constraint for statement rows?
  - Does the model handle repeated imports of overlapping date ranges without duplicating transactions?
- Are NOT NULL and CHECK constraints used where the domain requires them?
- Are enums/lookup values constrained, not free text?

### Normalization and modeling
- Is the model normalized enough to avoid update anomalies?
- Where denormalized, is that a deliberate, justified choice?
- Are there synthetic/mirror rows that must be kept in sync manually? Flag the consistency burden.
- Is `transactions` (or the core table) clearly the source of truth, with others referencing it?
- Are categories, accounts, and statements modeled as first-class entities where needed?
- Transfers:
  - How are two-legged transfers modeled?
  - Are transfer links represented via an explicit link table, not by mutating ledger rows?
  - Can a transfer be unlinked or re-linked without losing transaction history?
- Soft retirement:
  - Are accounts and categories retired via an `is_active` flag, not hard-deleted?
  - Does retiring an entity preserve all historical ledger relationships?
- Balance checkpoints:
  - Is there a mechanism for statement closing-balance checkpoints?
  - Can calculated running balances be verified against statement closing balances?

### Multi-tenancy
- Does every user-owned table carry a non-nullable owner/`user_id` key from day 1?
- Is data isolation between users enforceable at the schema level? Avoid implicit scoping via multi-hop joins.
- Are uniqueness constraints tenant-scoped (e.g. `UNIQUE (user_id, name)`), so two users can have same-named categories/accounts?
- Do foreign keys ensure a child cannot reference a parent owned by a different user?

### Indexing and query performance
- Are composite indexes created for high-frequency queries (e.g. `(user_id, account_id, txn_date DESC)`)?
- Do index column orders match left-prefix query patterns?
- Are lookup indexes present for dedup matching during import?
- Are partial indexes used for filtered workflows (unmatched transactions, active categories)?
- Is redundant indexing avoided to limit write overhead?

### Indian financial context
- Are Indian statement fields represented (UPI refs, bank/card identifiers, IMPS/NEFT references)?
- Is the financial year / assessment year handled where reporting needs it?

### Extensibility and evolution
- Can new statement formats or account types be added without reshaping the core?
- What happens to historical data when categories or rules change?
- Are migrations going to be painful given the current keys and constraints?
- Is every non-obvious schema choice documented with context and trade-offs?
- Are table and column names consistent, descriptive, and aligned with the spec's domain terms?

### Consistency with the spec
- Does the model support every feature and flow in the spec?
- Is anything in the spec impossible or awkward with this model?

## How to report

Group findings by severity. Skip a heading with nothing under it.
For each finding: state the problem, why it matters, and a concrete schema/constraint suggestion. Point to specific tables, columns, or relationships.

- **Blocker** — floating-point money, missing tenant scoping, loss of raw import data, or missing FK constraints that risk ledger corruption.
- **High** — an index gap causing table scans on core queries, missing composite uniqueness on tenant data, or cascade-delete risk.
- **Medium** — inconsistent naming, missing check constraints, or ambiguous column semantics.
- **Low / Suggestion** — minor optimization, documentation, or indexing hint.
